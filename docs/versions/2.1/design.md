# 2.1 功能设计与数据口径

## 三种记录各司其职

长期任务 `Project` 表示一个持续目标或交付，日程 `Task` 表示当天的一段行动，成果记录 `ProjectEntry` 表示有日期的进展/里程碑/卡点。一个长期任务对应多个日程和多个成果记录；一个日程最多关联一个长期任务，防止重复计时。未来事件不关联长期任务，也不进入完成率与实际时长统计。

大类复用原有分类管理，事业、生活、娱乐等由用户配置。标签可多选和自行输入，去重，按当前文本精确匹配；不自动合并 AI/ai。合作人用名称数组，不传送邀请。

任务拥有稳定 ID、创建时间、1–5 重要度、起始日期和可空结束日期。结束日期非空代表完成。阶段成果与进展保留独立日期。卡点单独保留解决状态及解决日期；已解决内容仍留在时间线上，最新未解决卡点按记录日期降序选取。

## 统计定义

- 累计实际投入：关联的行动时间块 `actual` 分钟之和；计划时长另外累加 `end-start`，互不代替。
- 行动天数：截至今天，至少一个关联日程有实际投入、正进度或进展文字的去重日期。仅安排但未开始不算行动。
- 最近进展：已发生的上述日程日期、成果记录日期与卡点解决日期的最大值。修改任务名称、标签不算新进展；补记的进展按所属日期排序。
- 持续时间：起始日至结束日（未完成则今天）的自然日，含首尾。计划未来开始的任务未开始时显示 0 天。
- 完成率：Σ（计划分钟×进度）÷Σ计划分钟；未来事件排除，无计划显示 0。不把一个长期任务的完成状态当作所有日程完成。
- 正事时长：原分类的 `focus` 开关决定，累计实际分钟；任务标签、重要度不改变规则。

## 复盘和 Excel

每日一篇；每个周一为起点的一周一篇。复盘不计入行动时长或自动计为完成，避免写字就“刷分”。复盘编辑有明确保存按钮；离开前需保存。

Excel 使用数值单元格、冻结标题行、自动筛选、可读列宽和中文表名。用户文本写成字符串而非公式，避免以 `=` 开头的笔记被当作公式执行。周/月聚合都截取至当前报告边界，避免重复累计边界日期。未关联长期任务的日程仍完整导出。

复盘按日期区间相交收录，跨月周复盘可能出现于相邻两个月的报告，其完整起止日期保留在表中。成果/卡点按记录日期或解决日期落入区间收录。产品成果表只列本期开始、完成、行动、记录成果或解决卡点的任务，元数据/总时长注明“当前”。历史报表是当前数据快照，补记会影响重导出的历史结果。

## 持久化与兼容

2.1 在原 journal JSON 中新增 `schemaVersion`、`projects`、`reviews`，日程可选 `projectId`，不修改 SQLite 表结构。校验引用、大类、日期、数值边界、重复 ID、记录数量与文本长度。现有修订号保护、防跨来源写入、账号隔离与 1.5 MB 请求上限保留。

旧备份合法且可以恢复，恢复旧备份意味着长期任务与复盘为空，界面仍会先提示覆盖全部记录。已升级账号若收到无 2.1 版本标识的旧页面写入则拒绝，并要求刷新。升级不运行生产种子数据。数据库继续位于 Git 之外。

## 双站点维护

公司入口保持 Next.js/SQLite/账号登录。`sites-adapter/` 只替换托管平台专属身份、状态 API、数据库适配和构建入口；`scripts/prepare-sites.mjs` 从公司源码生成一个独立的空目录。不得把 Sites 适配直接覆盖到公司 main。新站默认仅创建者可访问，记录独立；需要迁移时通过用户自己导出的 JSON 导入。
